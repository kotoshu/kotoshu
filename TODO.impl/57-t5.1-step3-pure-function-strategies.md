# 57 — T5.1 step 3: Strategies as pure functions

## Goal

Finish the MECE refactor of `suggestions/strategies/` started in
TODO 56 T5.1. Steps 1 and 2 are done (PRs #75, #76):

- Step 1 (PR #75): Extracted `SuggestionSet#deduplicate!` as a named
  method with a `duplicates_removed` counter. Was previously buried
  as a side effect inside `sort_and_limit!`.
- Step 2 (PR #76): `CompositeStrategy#generate` now collects all
  strategy outputs via `flat_map` and builds one `SuggestionSet` at
  the end — was running sort/dedup/limit N times per merge.

Step 3 remains: make strategies **pure functions** of
`(word, dictionary) → candidates`, with no shared state and no
global config reads.

## Current state (what's wrong)

`EditDistanceStrategy` is the worst offender. Its constructor:

```ruby
def initialize(name: :edit_distance, language_code: 'en',
               keyboard_layout: nil, **config)
  super(name: name, **config)
  @language_code = language_code
  @keyboard_layout = keyboard_layout
  @frequency_data = load_frequency_data(language_code)     # disk IO at construction
  @keyboard_layout = resolve_keyboard_layout(keyboard_layout)
end
```

Consequences:

- Strategy is **bound to one language** at construction. Switching
  languages requires a new strategy instance (and re-loads frequency
  data from disk).
- Strategy reads `Kotoshu::Cache::FrequencyCache` (global state) via
  `load_frequency_data`. Hard to test without network/disk fixtures.
- Strategy is **stateful** — same instance returns different scores
  for the same `(word, dictionary)` pair if the underlying cache
  changes between calls.
- Per-document configuration (different frequency list, different
  keyboard layout) requires reconstructing the strategy pipeline.

`SymspellStrategy`, `NgramStrategy`, `PhoneticStrategy` have the
same shape; `SemanticStrategy` already takes its model via context.

## Target design

Strategies become stateless. Per-call state (language, keyboard,
frequency data) flows through `Suggestions::Context`.

```ruby
class EditDistanceStrategy < BaseStrategy
  def generate(context)
    keyboard = context.keyboard_layout      # was @keyboard_layout
    frequency = context.frequency_data      # was @frequency_data
    # ... pure function of (context.word, context.dictionary, keyboard, frequency)
  end
end
```

`Suggestions::Context` gains accessors for the data the strategies
need. A `ContextBuilder` (new) is responsible for loading the
language-specific data lazily, keyed by `language_code` and
`dictionary.language_code`. The builder is the only place that
touches `Cache::FrequencyCache` and `Keyboard::Registry`.

## Phases

### Phase A — Move keyboard_layout to Context

`KeyboardProximityStrategy` and `EditDistanceStrategy` both currently
hold `@keyboard_layout`. Move to Context. Strategies read
`context.keyboard_layout`.

### Phase B — Move frequency_data to Context

`EditDistanceStrategy` currently calls `load_frequency_data` in
`initialize`. Move the loader into a `Suggestions::ContextBuilder`
that produces a Context with `frequency_data` populated.

### Phase C — Drop strategy configuration coupling

Stop passing `language_code` to strategy constructors. The language
is already on `context.dictionary.language_code`. Strategies read
language from context, not from their own configuration.

### Phase D — Verify strategies are pure

Add a property test:

```ruby
it "strategy.generate(ctx) returns the same SuggestionSet across calls" do
  # ... generate twice with same context, expect identical results
end
```

## Acceptance criteria

- [ ] No strategy reads `Cache::FrequencyCache` or
      `Keyboard::Registry` directly.
- [ ] No strategy accepts `language_code` or `keyboard_layout` in
      its constructor.
- [ ] `Suggestions::Context` carries all per-call state.
- [ ] Strategies pass a purity property test (same context → same
      result, no global-state-dependent variation).
- [ ] Existing strategy specs continue to pass (or are updated to
      build context with the new state).
- [ ] Generator (orchestrator) constructs the ContextBuilder once
      per pipeline run, not once per strategy.

## Why this matters

- **Per-document configuration.** A multi-language document needs
  different strategies per segment. Today, the strategy instances
  are bound to one language at construction — `MultiLanguageChecker`
  has to rebuild the pipeline per segment.
- **Testing.** Stateful strategies that hit disk in their
  constructor are slow to test and require network/disk fixtures.
  Pure-function strategies only need a Context value object.
- **Parallelism.** `ParallelChecker` can't safely share strategy
  instances across threads today because the strategies hold mutable
  state. Pure functions are trivially thread-safe.

## Dependencies

- **Blocked by:** none.
- **Blocks:** TODO 52 (multi-language document checking) becomes

## Out of scope

- Changing the suggestion algorithm itself.
- Removing the `BaseStrategy` inheritance hierarchy.
- Renaming or restructuring the existing strategy classes.
